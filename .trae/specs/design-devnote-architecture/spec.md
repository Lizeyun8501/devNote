# DevNote 先进云笔记架构设计 Spec

## Why
现有云笔记产品（Obsidian、Notion、思源笔记、Joplin、AppFlowy、Anytype、Notesnook）各自存在架构缺陷：或受限于 Electron 性能瓶颈，或依赖云端导致离线不可用，或缺乏端到端加密，或插件生态封闭。DevNote 旨在融合各产品优势、规避其设计缺陷，为技术开发者打造一款本地优先、企业级安全、高性能、高可扩展的云笔记应用。

## What Changes
- 设计五层解耦架构：表示层（Flutter+Qt）、桥接层（Dart FFI+C ABI+gRPC/WebSocket）、核心业务层（Rust+Go）、本地持久化层（SQLite+加密文件存储）、云端适配层（自建同步服务+云存储SDK）
- 新增对象化数据模型引擎（借鉴 AnyType）
- 新增关系数据库引擎（借鉴 Notion/AppFlowy）
- 新增 Canvas 渲染引擎（借鉴 Obsidian Canvas）
- 云端适配层强化 P2P 同步协议（借鉴 Anytype）
- 设计基于 WebAssembly 沙箱的插件系统
- 设计面向个人知识管理的增强功能（闪卡、知识体系梳理、学习统计、画布知识连接、对象化关系浏览、数据库视图仪表盘）
- 最大化复用开源组件：AppFlowy、思源笔记、Joplin、Notesnook、Anytype 的核心代码
- 设计全链路性能优化方案（启动速度、大文档编辑、内存占用、同步性能、Canvas 性能、对象化模型性能）
- 规划四阶段渐进式开发路线图
- 规划三阶段未来演进路线图

## Impact
- Affected specs: 全新项目，无已有 spec 受影响
- Affected code: 全新代码库，核心复用来源包括 AppFlowy（Flutter UI + Rust 引擎）、思源笔记（块编辑 + 知识图谱 + SQLite 存储）、Joplin（同步协议 + 格式导入导出）、Notesnook（加密引擎）、Anytype（对象化模型 + P2P 同步）

## ADDED Requirements

### Requirement: 五层解耦架构
系统 SHALL 采用分层解耦架构设计，包含五个逻辑层：表示层、桥接层、核心业务层、本地持久化层、云端适配层，各层通过标准 FFI/API 接口通信，完全解耦。

#### Scenario: 层级间通信
- **WHEN** 表示层发起用户操作请求
- **THEN** 请求经桥接层路由转发至核心业务层对应模块，业务层处理后将结果经桥接层返回表示层渲染

#### Scenario: 层级独立替换
- **WHEN** 需要替换某一层的技术实现
- **THEN** 只需实现该层的标准接口，不影响其他层的功能

### Requirement: 本地优先架构
系统 SHALL 将本地数据存储、访问、处理能力置于优先级首位，所有笔记数据的读写、编辑、检索逻辑默认在本地设备完成，云端仅作为加密备份与多设备同步的中转载体。

#### Scenario: 离线编辑
- **WHEN** 用户在无网络环境下编辑笔记
- **THEN** 所有编辑操作正常完成，数据持久化到本地，网络恢复后自动同步增量变化到云端

#### Scenario: 数据主权
- **WHEN** 用户选择停止使用云端同步
- **THEN** 所有数据仍完整保留在本地设备，用户可正常使用全部本地功能

### Requirement: 表示层设计
系统 SHALL 采用 Flutter+Qt 混合架构构建表示层：桌面端常规界面用 Flutter，高级编辑界面用 Qt；移动端用 Flutter 统一构建；原生能力通过 Platform Channel 适配。

#### Scenario: 桌面端高级编辑
- **WHEN** 用户在桌面端打开大文档进行编辑
- **THEN** 编辑界面由 Qt 框架渲染，提供原生级响应速度与资源控制能力

#### Scenario: 移动端一致性体验
- **WHEN** 用户在 iOS 或 Android 设备上使用应用
- **THEN** UI 表现、交互逻辑与桌面端保持一致，同时适配移动端原生能力（生物识别、文件访问等）

### Requirement: Canvas 无限画布组件
系统 SHALL 提供 Canvas 无限画布组件，基于 Flutter CustomPaint/InteractiveViewer 或 Qt QGraphicsScene 实现，支持自由拖拽、缩放、连接块、手绘风格，允许用户在无限画布上组织笔记块、图片、箭头等。

#### Scenario: 画布知识连接
- **WHEN** 用户在画布上拖拽笔记块并用箭头连接
- **THEN** 系统保存画布数据（nodes 和 edges 的 JSON 格式），并在知识图谱中体现关联关系

### Requirement: 桥接层设计
系统 SHALL 采用 Dart FFI + C ABI + gRPC/WebSocket 混合通信方案构建桥接层：桌面端基于 Dart FFI 通过 C ABI 通信；移动端/远程场景基于 gRPC 或 WebSocket 通信；所有端采用统一通信协议。

#### Scenario: 桌面端高频数据交换
- **WHEN** 用户在桌面端进行编辑操作
- **THEN** UI 层通过 Dart FFI 直接调用核心业务层 Rust/C++ 逻辑，通过 C ABI 传输二进制数据，减少转换开销

#### Scenario: 通信异常处理
- **WHEN** 跨端通信发生超时或异常
- **THEN** 桥接层自动重连并重试请求，同时向表示层返回异常状态通知

### Requirement: 核心业务层设计
系统 SHALL 采用 Rust+Go 混合架构构建核心业务层：CPU 密集型场景（同步、加密、压缩、解析、校验、全文检索）用 Rust；业务逻辑场景（元数据管理、规则校验、标签/目录管理、知识关系计算）用 Go；暴露标准 C ABI 或 gRPC 接口。

#### Scenario: 加密操作性能
- **WHEN** 系统对笔记数据进行端到端加密
- **THEN** 加密操作由 Rust 引擎执行，利用其内存安全特性，避免内存泄漏和数据异常

#### Scenario: 业务规则校验
- **WHEN** 用户创建或修改笔记的目录结构
- **THEN** Go 引擎执行业务规则校验，利用协程能力高效处理事务

### Requirement: 块编辑引擎
系统 SHALL 提供块编辑引擎，处理块级编辑操作，解析 Markdown/富文本内容格式，维护笔记内容的结构变化、计算关系元数据、校验用户输入合法性。复用思源笔记核心块级编辑引擎逻辑和 AppFlowy 块级实时协作逻辑，移植 pulldown-cmark Rust 库。

#### Scenario: 块级编辑
- **WHEN** 用户在编辑器中插入代码块、LaTeX 公式、流程图等
- **THEN** 块编辑引擎解析内容格式，维护块结构，计算关系元数据

#### Scenario: 多端实时协作
- **WHEN** 多个设备同时编辑同一块内容
- **THEN** 块编辑引擎通过 CRDT 算法自动合并编辑冲突

### Requirement: 同步引擎
系统 SHALL 提供同步引擎，实现增量同步逻辑、CRDT 算法的多端编辑冲突合并，以及同步数据的压缩、校验、加密、断点续传，维护每个设备的同步状态和历史操作日志。复用 Joplin 同步协议、AppFlowy CRDT 算法、Anytype P2P 同步逻辑，移植 rdiff Rust 库。

#### Scenario: 增量同步
- **WHEN** 用户在设备 A 修改笔记后，设备 B 发起同步
- **THEN** 同步引擎仅传输修改的增量数据，设备 B 成功合并变更

#### Scenario: 冲突合并
- **WHEN** 两个设备同时修改同一笔记的不同部分
- **THEN** CRDT 算法自动合并冲突，保留双方修改；若修改同一部分，生成冲突备份文件供用户手动选择

### Requirement: 加密引擎
系统 SHALL 提供加密引擎，封装端到端加密逻辑、本地数据加密逻辑及密钥安全管理逻辑，对所有出入业务层的数据进行加密解密处理。复用 Notesnook 的 XChaCha20-Poly1305 算法、Argon2 密钥派生函数、零知识架构，移植 rustcrypto 加密算法库。

#### Scenario: 端到端加密同步
- **WHEN** 笔记数据同步到云端
- **THEN** 数据在本地加密后才传输，服务端仅存储密文，无法解密用户数据

#### Scenario: 零知识架构
- **WHEN** 云存储服务器被攻破
- **THEN** 攻击者无法获取用户原始数据，因为服务端不保存任何可用于解密的密钥信息

### Requirement: 检索引擎
系统 SHALL 提供检索引擎，实现全文检索、高级筛选、关键词高亮逻辑，维护笔记内容和元数据的倒排索引。复用思源笔记全文检索引擎逻辑，移植 tantivy Rust 全文检索库。

#### Scenario: 全文检索
- **WHEN** 用户输入关键词进行搜索
- **THEN** 检索引擎在毫秒级返回匹配结果，关键词高亮显示，支持多条件组合筛选

### Requirement: 知识图谱引擎
系统 SHALL 提供知识图谱引擎，处理双向链接、标签的关系计算逻辑，维护笔记间的关系索引，提供图谱可视化数据。复用思源笔记双向链接和关系索引计算逻辑。

#### Scenario: 双向链接查询
- **WHEN** 用户查看某篇笔记的反向链接
- **THEN** 知识图谱引擎返回所有引用该笔记的其他笔记列表，并在图谱中可视化展示关联关系

### Requirement: 对象化数据模型引擎
系统 SHALL 提供对象化数据模型引擎，将所有内容（笔记、任务、文件、关系）抽象为统一的对象（Object），每个对象拥有类型（Type）、属性（Relation）、链接（Link），支持灵活的多态关联。借鉴 Anytype 对象模型，适配 Rust 实现。

#### Scenario: 对象创建与关联
- **WHEN** 用户创建一个"项目"对象并关联多个"任务"对象
- **THEN** 对象化模型引擎创建对象实例、建立关联关系，支持后续的关系查询和版本追踪

#### Scenario: 块提升为对象
- **WHEN** 用户将编辑器中的某个块提升为独立对象
- **THEN** 该块获得独立的对象标识和属性，可被其他对象引用，同时保留在原文档中的嵌入关系

### Requirement: 关系数据库引擎
系统 SHALL 提供关系数据库引擎，基于 SQLite 存储行、列、单元格数据，支持表格/看板/日历视图、公式、筛选、排序、分组操作，可与块级内容双向绑定。复用 AppFlowy 的 appflowy-database 核心代码。

#### Scenario: 数据库视图切换
- **WHEN** 用户在表格视图和看板视图之间切换
- **THEN** 关系数据库引擎基于同一数据源渲染不同视图，数据实时同步

#### Scenario: 公式计算
- **WHEN** 用户在数据库单元格中输入公式
- **THEN** 引擎解析公式并计算结果，支持跨行引用和聚合函数

### Requirement: Canvas 渲染引擎
系统 SHALL 提供 Canvas 渲染引擎，负责将画布上的节点（块、图片、文件）和边（连接关系）转换为内存数据结构，处理布局计算、缩放、拖拽、自动对齐逻辑，输出渲染指令给表示层。复用 Obsidian Canvas 数据模型（JSON 格式：nodes 和 edges）。

#### Scenario: 画布布局计算
- **WHEN** 用户在画布上添加或移动节点
- **THEN** Canvas 渲染引擎重新计算布局，输出渲染指令，表示层实时更新画布显示

### Requirement: 格式解析引擎
系统 SHALL 提供格式解析引擎，处理笔记的格式转换逻辑，解析导入的第三方格式，导出为目标格式。复用 Joplin 格式导入导出逻辑和思源笔记内部存储格式解析逻辑。

#### Scenario: 批量导入
- **WHEN** 用户从 Obsidian Vault 批量导入笔记
- **THEN** 格式解析引擎解析 Markdown 文件和元数据，转换为 DevNote 内部格式，保留双向链接和附件

### Requirement: 本地持久化层设计
系统 SHALL 采用 SQLite + 加密文件系统的混合存储方案：结构化数据存储在 SQLite 加密数据库中；非结构化数据以加密二进制块文件存储；SQLite 中维护非结构化数据文件的元数据索引；可选支持 IPFS 块存储。

#### Scenario: 数据读写
- **WHEN** 用户创建一篇包含图片的笔记
- **THEN** 笔记元数据和文本内容存入 SQLite 加密数据库，图片附件以加密二进制块文件存储，两者通过元数据索引关联

#### Scenario: IPFS 块存储
- **WHEN** 用户启用 IPFS 块存储选项
- **THEN** 大块二进制内容存储为 IPFS 块，利用内容寻址和去重能力，本地保留 SQLite 索引和加密块缓存

### Requirement: 云端适配层设计
系统 SHALL 采用自建同步服务 + 第三方云存储 SDK 的混合方案：Go 语言自建同步服务处理状态控制和冲突仲裁；兼容 Nextcloud、Dropbox、OneDrive、WebDAV、S3 协议存储；HTTP/2+TLS1.3 传输协议；增加 P2P 同步通道（WebRTC/libp2p）。

#### Scenario: 多存储后端切换
- **WHEN** 用户从 WebDAV 切换到 S3 兼容存储
- **THEN** 云端适配层自动适配新存储后端，无需迁移已有数据格式

#### Scenario: P2P 同步
- **WHEN** 两台设备在同一局域网内
- **THEN** 设备之间通过 libp2p 直接传输加密数据块，不经过中央服务器，中央服务器仅用于信令交换和公钥分发

### Requirement: 插件系统
系统 SHALL 提供基于 WebAssembly 沙箱的插件系统，支持动态加载、版本管理、权限控制、代码审计、数据隔离、沙箱逃逸防护，提供官方插件市场。

#### Scenario: 插件安装与运行
- **WHEN** 用户从插件市场安装一个插件并启用
- **THEN** 插件代码在独立 WASM 虚拟机中运行，只能通过标准 API 访问用户授权的数据和功能

#### Scenario: 插件权限控制
- **WHEN** 插件请求访问笔记数据权限
- **THEN** 系统弹出权限请求提示，用户可选择授予或拒绝，插件只能在授予的权限范围内操作

#### Scenario: 插件扩展能力
- **WHEN** 开发者编写插件添加自定义画布节点类型
- **THEN** 通过 Canvas 插件 API 注册新节点类型，自动集成到画布交互中

### Requirement: 性能优化
系统 SHALL 在各层级实现针对性性能优化：启动时间 1 秒以内（懒加载+预编译缓存+连接池）；大文档支持百万字级别（虚拟滚动+增量解析+分块存储）；内存优化（内存池+图片压缩+GC 优化）；同步优化（增量同步+断点续传+并发同步）；Canvas 优化（离屏渲染+瓦片缓存+增量布局）；对象化模型优化（邻接表存储+批量事务写入）。

#### Scenario: 百万字大文档编辑
- **WHEN** 用户打开一篇百万字的笔记
- **THEN** 编辑器仅渲染当前视口内容，编辑响应时间不超过 50ms，内存占用稳定

#### Scenario: 启动速度
- **WHEN** 用户启动应用
- **THEN** 核心基础模块在 1 秒内加载完成，其他模块按需懒加载

### Requirement: 间隔重复闪卡功能
系统 SHALL 集成 Anki 风格间隔重复算法，支持用户将笔记中的重点内容一键转化为闪卡，支持基础问答、填空、cloze 闪卡类型，自动安排复习计划，提供复习进度统计和记忆曲线展示。

#### Scenario: 笔记转闪卡
- **WHEN** 用户选中笔记中的重点内容并点击"生成闪卡"
- **THEN** 系统自动创建闪卡，根据间隔重复算法安排首次复习时间

### Requirement: 知识体系梳理工具
系统 SHALL 提供可视化知识体系梳理工具，支持知识图谱筛选搜索、学习进度跟踪、标签化管理。

#### Scenario: 学习目标跟踪
- **WHEN** 用户设置学习目标并关联知识节点
- **THEN** 系统自动跟踪学习进度，提醒用户完成学习任务

### Requirement: 学习数据统计与分析
系统 SHALL 提供个人学习数据统计与分析功能，统计笔记创建/编辑/复习时间，分析知识关联和盲区，生成月度/年度学习报告。

#### Scenario: 学习报告生成
- **WHEN** 用户查看月度学习报告
- **THEN** 系统展示笔记创建数量、编辑频率、复习完成率、知识覆盖度等统计数据

### Requirement: 数据开放与可移植性
系统 SHALL 采用开放标准数据格式，提供完善的导入导出、备份恢复能力，支持与主流笔记工具的无损数据迁移。

#### Scenario: 数据导出
- **WHEN** 用户选择将所有笔记导出
- **THEN** 系统支持以 Markdown、PDF、HTML 等多种格式批量导出到用户指定目录

### Requirement: 可观测性
系统 SHALL 在核心业务模块中埋点完善的日志、监控、异常上报机制，便于排查缺陷、优化性能和保障服务稳定。

#### Scenario: 异常排查
- **WHEN** 同步引擎发生异常
- **THEN** 系统记录详细日志并上报异常信息，开发者可通过日志快速定位问题

### Requirement: 四阶段渐进式开发
系统 SHALL 按四阶段渐进式开发：阶段一（基础框架与核心能力搭建）、阶段二（完善本地笔记管理与核心业务能力）、阶段三（实现云同步与安全能力闭环）、阶段四（优化知识关联能力、适配技术开发场景）。

#### Scenario: MVP 交付
- **WHEN** 四个开发阶段全部完成
- **THEN** 产出覆盖 Windows、macOS、Linux、Android、iOS 全平台的 MVP 版本

### Requirement: 三阶段未来演进路线图
系统 SHALL 规划三阶段未来演进：短期（0-6 个月）MVP 完善与生态建设；中期（6-18 个月）AI 增强与协作能力；长期（18 个月以上）全场景知识管理中枢。

#### Scenario: 短期演进
- **WHEN** MVP 发布后的 0-6 个月内
- **THEN** 上线插件市场、完善数据迁移工具、优化移动端体验

#### Scenario: 中期演进
- **WHEN** 产品进入 6-18 个月阶段
- **THEN** 集成本地 AI 模型、增加团队协作能力、完善 P2P 同步、支持离线 AI 推理

#### Scenario: 长期演进
- **WHEN** 产品进入 18 个月以上阶段
- **THEN** 打造全场景知识管理中枢、支持多模态内容管理、自定义工作流、开源社区建设
