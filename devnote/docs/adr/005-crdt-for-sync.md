# ADR 005: CRDT + HLC 用于无冲突同步

| 属性 | 值 |
|------|------|
| **标题** | 使用 CRDT（无状态复制数据类型）+ HLC（混合逻辑时钟）实现无冲突同步 |
| **状态** | Accepted |
| **日期** | 2025-02-20 |
| **决策者** | DevNote 核心架构团队 |

## 上下文

DevNote 需要支持多端（桌面、移动、Web）离线编辑后自动合并，要求同步机制满足：

1. **无冲突合并**：多端同时编辑同一笔记时，最终状态一致，不需要用户手动解决冲突（尽可能减少）。
2. **离线优先**：网络中断时本地编辑不受影响，恢复后自动同步。
3. **因果顺序**：操作的因果关系必须正确保留，避免逻辑不一致。
4. **幂等性**：同一操作重复应用不改变最终状态。

### 备选方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| **CRDT + HLC** | 强最终一致性、离线可用、无中央协调、自动合并 | 状态膨胀（tombstone 积累）、元数据开销、算法复杂 |
| OT（操作转换） | Google Docs 验证、实时协作体验好 | 需要中央服务器协调、离线支持复杂、算法复杂 |
| 最后写入胜出 (LWW) | 简单、易实现 | 丢失并发写入数据、用户体验差 |
| Git 式合并 | 版本追溯、手动合并控制 | 冲突需要用户介入、不适合细粒度编辑 |
| 事件溯源 | 完整历史、可回放 | 存储开销大、合并策略仍需设计 |

## 决策

选择 **CRDT（无状态复制数据类型）+ HLC（混合逻辑时钟）** 作为 DevNote 的同步机制。

### 核心设计

#### CRDT 类型

| 数据类型 | CRDT 类型 | 用途 |
|---------|-----------|------|
| 笔记文本 | LWW-Register + Sequence CRDT | 块级文本编辑合并 |
| 笔记属性 | LWW-Map | 标题、创建时间等属性同步 |
| 标签列表 | G-Set / 2P-Set | 标签添加/删除 |
| 文件夹层级 | OR-Set + Tree CRDT | 文件夹嵌套结构 |
| 删除标记 | Tombstone Set | 软删除跨端传播 |

#### HLC（混合逻辑时钟）

使用 Hybrid Logical Clock 替代纯 wall-clock 时间戳：

```rust
pub struct HLC {
    physical: i64,  // 物理时间戳 (ms)
    logical: u32,   // 逻辑计数器
    site_id: String, // 站点标识
}

impl HLC {
    pub fn update(&mut self) {
        let now = current_time_ms();
        if now > self.physical {
            self.physical = now;
            self.logical = 0;
        } else {
            self.logical += 1;
        }
    }

    pub fn merge(&mut self, other: &HLC) {
        self.physical = self.physical.max(other.physical);
        if self.physical == other.physical {
            self.logical = self.logical.max(other.logical);
        } else if self.physical < other.physical {
            self.logical = 0;
        }
    }
}
```

HLC 相比纯 wall-clock 的优势：
- **因果关系**：逻辑计数器保证同一物理时钟内的操作有序
- **时钟漂移容忍**：即使物理时钟有偏差，逻辑计数器也能正确排序
- **确定性合并**：相同的操作集在任何站点合并结果一致

### 同步流程

```
本地编辑                    同步                    远端
   │                        │                        │
   ├── 生成操作 ───────────>│                        │
   │  (HLC 时间戳)           │                        │
   ├── 应用本地 ───────────>│                        │
   │                        │── 推送操作 ───────────>│
   │                        │                        │
   │                        │<── 拉取变更 ───────────│
   │                        │                        │
   │<── 合并变更 ───────────│                        │
   │  (CRDT merge)          │                        │
```

### 实现要点

1. **幂等去重**：使用操作 ID 集合跟踪已应用的操作，避免重复应用。
2. **Tombstone 清理**：定期压缩已确认所有站点都已看到的 tombstone。
3. **事务包裹**：每次同步操作包裹在 SQLite 事务中，失败时自动回滚。
4. **Sync Log**：维护本地操作日志，用于增量同步和断点续传。

## 后果

### 正面

- **离线优先**：无网络时本地编辑完全可用，恢复后自动合并。
- **无冲突合并**：CRDT 数学保证最终一致性，减少用户手动解决冲突的场景。
- **去中心化**：不依赖中央服务器，支持 P2P 同步。
- **因果一致性**：HLC 保证操作因果顺序正确。

### 负面

- **状态膨胀**：Tombstone 和操作日志会随时间增长，需要定期清理（compact）。
- **元数据开销**：每个操作携带 HLC 时间戳（~20 bytes），相比 LWW 增加存储开销。
- **实现复杂度**：CRDT 算法需要仔细实现，merge 非真正幂等（已识别为 P0 问题需要修复）。
- **用户可预测性**：自动合并的结果有时可能不符合用户直觉（如两个编辑插入同一位置）。

### 已识别风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| merge 非真正幂等 | 维护持久化的 `applied_ops` HashSet，不依赖当前操作集合 |
| Tombstone 膨胀 | 定期 compact，清理已确认全局可见的 tombstone |
| 同步失败无回滚 | 每次 sync 包裹在 SQLite 事务中 |
| 时钟漂移 | HLC 逻辑计数器容忍物理时钟偏差；不支持 NTP 时间回跳 |
